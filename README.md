# Beetroot EMB 4

Навчальний проєкт для STM32F411CE (плата BlackPill), що демонструє Message Buffer у FreeRTOS.

## Що демонструє проєкт

`messageTx` надсилає текстові команди через Message Buffer таску `messageRx`, який керує трьома LED-виходами в циклі:

1. Увімкнути LED1 (PA1), зачекати 1 с.
2. Увімкнути LED2 (PA2), зачекати 1 с.
3. Увімкнути LED3 (PA3), зачекати 1 с.
4. Вимкнути LED3, LED2, LED1 з інтервалом 1 с між командами.

Після вимкнення LED1 таск чекає ще 1 с і повторює цикл.

Під'єднайте кожен пін до анода світлодіода через окремий резистор 330–1000 Ом, катоди — до GND. Вбудований світлодіод PC13 не використовується демонстрацією. Світлодіоди працюють і без USB.

Порти й піни задаються макросами у `Src/app/main_app.cpp`; усі три піни мають належати одному порту. При зміні порту також змініть макрос увімкнення його тактування `LED_GPIO_CLK_ENABLE()`.

## IPC: Message Buffer

Кожне повідомлення — окрема текстова команда, наприклад `LED1 ON` (7 байтів) або `LED1 OFF` (8 байтів). Message Buffer передає повідомлення різної довжини та зберігає їхні межі: отримувач читає одну команду за раз.

### Як працює приклад

1. `main_cpp()` вимикає світлодіоди та створює буфер викликом `xMessageBufferCreateStatic()`, передаючи статичні масив даних і блок керування.
2. `messageTx` викликає `xMessageBufferSend(led_message_buffer, message, length, portMAX_DELAY)`. Він передає `strlen(message)` байтів без завершального `'\0'`. Якщо місця для всього повідомлення бракує, таск чекає.
3. Між надсиланнями `messageTx` викликає `osDelay(1000U)`. Це 1000 тактів; при `configTICK_RATE_HZ = 1000` у цьому проєкті — приблизно 1 с.
4. `messageRx` викликає `xMessageBufferReceive(led_message_buffer, message, MAX_MESSAGE_BYTES, portMAX_DELAY)`. Якщо буфер порожній, таск чекає; інакше отримує одне повне повідомлення та його довжину в байтах.
5. Отримувач додає `'\0'` у свій локальний масив, перевіряє команду, змінює стан відповідного GPIO та виводить, наприклад, `[messageRx] LED1 ON (7 bytes)`.

Масив буфера має 80 байтів, з яких 79 доступні для повідомлень: один байт резервується реалізацією FreeRTOS. Кожне повідомлення займає до 15 байтів даних і 4 байти для довжини (`sizeof(configMESSAGE_BUFFER_LENGTH_TYPE)`). Наприклад, `LED1 ON` займає 7 + 4 = 11 байтів, а `LED1 OFF` — 8 + 4 = 12 байтів. Буфер уміщує щонайменше чотири повідомлення максимальної довжини.

Масив і блок керування виділені статично, без використання heap для буфера; таски створюються динамічно. Якщо отримувач надовго затримається і буфер заповниться, `xMessageBufferSend()` чекатиме вільного місця.

Локальний масив отримувача приймає до 15 байтів даних та має ще один байт для `'\0'`. Якщо наступне повідомлення не поміщається в наданий масив, `xMessageBufferReceive()` повертає 0 і залишає його в буфері; у цьому прикладі це вважається помилкою. Відправник також перевіряє довжину перед надсиланням.

Message Buffer призначений для **одного відправника та одного отримувача**. Для кількох відправників або отримувачів потрібна додаткова синхронізація відповідно до FreeRTOS API. Під час блокувального очікування Message Buffer використовує task notification всередині, тому не слід незалежно використовувати ті самі notification у цих тасках.

Щоб побачити очікування вільного місця, можна тимчасово додати `osDelay(2000U)` наприкінці циклу `messageRx`: відправник працюватиме швидше за отримувача, буфер з часом заповниться, і `xMessageBufferSend()` чекатиме вільного місця.

### Message Buffer з переривання

Для надсилання з ISR використовується `xMessageBufferSendFromISR()`. Наступний приклад ілюструє надсилання однієї команди:

```cpp
// Приклад для main_app.cpp, де доступний led_message_buffer.
extern "C" size_t SendLed1OnFromISR(void)
{
    const char message[] = "LED1 ON";
    BaseType_t higher_priority_task_woken = pdFALSE;

    size_t sent = xMessageBufferSendFromISR(
        led_message_buffer, message, sizeof(message) - 1U,
        &higher_priority_task_woken);
    portYIELD_FROM_ISR(higher_priority_task_woken);
    return sent;
}
```

- Функція копіює все повідомлення та повертає кількість записаних байтів. ISR не може чекати місця: якщо повідомлення не вміщується, повертається 0. Викликач має перевірити результат і зафіксувати втрату для подальшої обробки в таску.
- Якщо розблоковано таск з вищим пріоритетом, `higher_priority_task_woken` стане `pdTRUE`; `portYIELD_FROM_ISR()` запитає перемикання контексту після завершення ISR. `printf()` з ISR викликати не потрібно.

Це лише приклад: поточна програма не налаштовує переривання і не викликає цю функцію. Для використання потрібно оголосити її для обробника, налаштувати джерело та підтверджувати його переривання відповідно до периферії. Вмикайте ISR лише після створення буфера та запуску планувальника. Не використовуйте цей ISR одночасно з `messageTx` як другого відправника без додаткової синхронізації.

У цьому проєкті `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5`: ISR, який викликає FreeRTOS API, повинен мати числовий пріоритет NVIC від 5 до 15. Пріоритети 0–4 вищі й не можуть викликати API `FromISR`. Використовуйте групування пріоритетів NVIC, сумісне з FreeRTOS.

## Апаратна конфігурація

- MCU: STM32F411CEUx
- Framework: STM32Cube HAL
- Збірка та завантаження: PlatformIO, ST-Link

## Збірка

```
pio run
pio run -t upload
```

## Структура

- `Src/app/main_app.cpp` — Message Buffer і таски керування світлодіодами
- `Inc/FreeRTOSConfig.h` — конфігурація FreeRTOS
- `Src/main.c` — ініціалізація та запуск планувальника
