# Beetroot EMB 4

Навчальний проєкт для STM32F411CE (плата BlackPill), що демонструє Stream Buffer у FreeRTOS.

## Що демонструє проєкт

`streamTx` надсилає байти команд через Stream Buffer таску `streamRx`, який керує трьома LED-виходами в циклі:

1. Увімкнути LED1 (PA1), зачекати 1 с.
2. Увімкнути LED2 (PA2), зачекати 1 с.
3. Увімкнути LED3 (PA3), зачекати 1 с.
4. Вимкнути LED3, LED2, LED1 з інтервалом 1 с між командами.

Після вимкнення LED1 таск чекає ще 1 с і повторює цикл.

Під'єднайте кожен пін до анода світлодіода через окремий резистор 330–1000 Ом, катоди — до GND. Вбудований світлодіод PC13 не використовується демонстрацією. Світлодіоди працюють і без USB.

Порти й піни задаються макросами у `Src/app/main_app.cpp`; усі три піни мають належати одному порту. При зміні порту також змініть макрос увімкнення його тактування `LED_GPIO_CLK_ENABLE()`.

## IPC: Stream Buffer

Stream Buffer передає потік байтів і не зберігає меж викликів запису. Тому в цьому прикладі команди, як-от `LED1 ON` і `LED3 OFF`, відокремлюються символом нового рядка `'\n'`. Це правило програми, а не властивість Stream Buffer.

### Як працює приклад

1. `main_cpp()` створює статичний буфер через `xStreamBufferCreateStatic()`. Рівень пробудження `1U` означає, що таск, який чекає на порожній буфер, прокинеться, коли надійде хоча б один байт.
2. `streamTx` викликає `xStreamBufferSend()` для рядка разом із `'\n'`, але без завершального `'\0'`. Функція повертає кількість записаних байтів; якщо записано не все, таск надсилає решту. Між командами він чекає приблизно 1 с.
3. `streamRx` викликає `xStreamBufferReceive()` з масивом на **3 байти**. Виклик може повернути від 1 до 3 байтів, а не цілу команду. Кількість отриманих байтів виводиться в лог.
4. Отримувач додає байти до локальної команди. Коли приходить `'\n'`, він перевіряє зібрану команду, змінює відповідний GPIO та друкує, наприклад, `[streamRx] LED1 ON`.

Наприклад, `LED1 ON\n` може бути прочитано як `LED`, `1 O`, `N\n`. Так само два записи можуть потрапити в одну порцію читання: отримувач обробляє кожен байт і кожен роздільник, а не покладається на межі викликів. Команда може мати до 15 байтів без `'\n'`; якщо вона довша або некоректна, приклад повідомляє про помилку та викликає `Error_Handler()`.

Статичний масив має 80 байтів, з яких 79 доступні для потоку; один байт резервується реалізацією. На відміну від Message Buffer, Stream Buffer не додає перед кожним записом поле довжини. Масив і блок керування не використовують heap; таски створюються динамічно. Якщо отримувач затримається і буфер заповниться, відправник чекатиме вільного місця.

Stream Buffer призначений для **одного відправника та одного отримувача**. Для кількох відправників або отримувачів потрібна додаткова синхронізація відповідно до FreeRTOS API. Під час блокувального очікування Stream Buffer використовує task notification всередині, тому не слід незалежно використовувати ті самі notification у цих тасках.

Для роботи з ISR існують `xStreamBufferSendFromISR()` і `xStreamBufferReceiveFromISR()`. Вони не очікують даних або місця й можуть передати лише частину байтів: необхідно перевіряти повернуту кількість і обробляти решту. ISR не можна додавати як другого відправника або отримувача без відповідної синхронізації. У цьому проєкті ISR, що викликає FreeRTOS API, повинен мати числовий пріоритет NVIC від 5 до 15. Переривання для цього прикладу не налаштоване.

## Апаратна конфігурація

- MCU: STM32F411CEUx
- Framework: STM32Cube HAL
- Збірка та завантаження: PlatformIO, ST-Link

## Збірка

```
pio run
pio run -t upload
```

## Структура

- `Src/app/main_app.cpp` — Stream Buffer і таски керування світлодіодами
- `Inc/FreeRTOSConfig.h` — конфігурація FreeRTOS
- `Src/main.c` — ініціалізація та запуск планувальника
